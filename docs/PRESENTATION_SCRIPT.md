## Phase 1: สำรวจและวิเคราะห์ข้อมูล (EDA — Notebook 01)

### 1.1 ขั้นตอนนี้ทำทำไม? (Why do this?)
ก่อนจะป้อนข้อมูลเข้าโมเดล ต้องเข้าใจธรรมชาติของ Log ก่อน:
- Format เป็นอย่างไร มีจุดเชื่อมโยงระหว่างบรรทัดไหม?
- ข้อมูลมีความไม่สมดุล (Class Imbalance) ขนาดไหน?
- Log ผิดปกติมีความยาวหรือลักษณะต่างจากปกติอย่างไร?

### 1.2 Function สำคัญที่ใช้และเหตุผล

| Function / คำสั่ง | Library | หน้าที่การทำงาน | ทำไมถึงใช้คำสั่งนี้? |
|---|---|---|---|
| `re.findall(r'blk_-?\d+', line)` | `re` (Regex) | ดึงค่า `block_id` ออกจากบรรทัด Log | ใช้จัดกลุ่ม Log นับล้านบรรทัดให้กลายเป็น Session เดียวกันตาม Block ของ HDFS |
| `Counter(labels)` | `collections` | นับความถี่ของคลาสปกติ vs ผิดปกติ | สำรวจอัตราส่วน Class Imbalance พบว่าปกติมี 97.1% ผิดปกติมีเพียง 2.9% |
| `sns.boxplot()` / `sns.histplot()` | `seaborn` | พล็อตการกระจายตัวของความยาว Session | ตรวจสอบดูว่า Session ผิดปกติมีจำนวนบรรทัดมากกว่าปกติจริงหรือไม่ (พบว่า Anomaly มักมีความยาวเฉลี่ยสั้นกว่าหรือมี pattern แปลกแยก) |

> 🗣️ **บทพูดผู้บรรยาย (Phase 1):**
> *"ในระยะแรก เราเริ่มจากการทำ Exploratory Data Analysis หรือ EDA ครับ จากข้อมูลดิบ 11.17 ล้านบรรทัด เราพบข้อมูลสำคัญ 2 ประการ:*
>
> *1. **เราต้องจัดกลุ่มด้วย block_id:** Log แต่ละบรรทัดอยู่เดี่ยวๆ ไม่มีประโยชน์ เราจึงใช้ Regular Expression สกัด `block_id` เพื่อมัดรวม Log ที่ทำงานกับ Block เดียวกันให้กลายเป็น 1 Session ทั้งหมด 575,061 Sessions*
>
> *2. **ปัญหา Accuracy Paradox:** จากการนับ Label พบว่ามี Session ผิดปกติเพียง 2.9% เท่านั้น นั่นหมายความว่า หากระบบเดาว่า 'ปกติ' 100% ทุกครั้ง โมเดลจะได้ Accuracy ถึง 97.1% ทันทีแต่จับแฮกเกอร์ไม่ได้เลยแม้แต่คนเดียว! ดังนั้นเราจึงตัดสินใจใช้ **F1-Score** เป็นตัวชี้วัดหลักแทน Accuracy ครับ"*

## Phase 2: Log Parsing & Data Preparation (Notebook 02)

### 2.1 ขั้นตอนนี้ทำทำไม? (Why do this?)
คอมพิวเตอร์และโมเดล ML/DL ไม่เข้าใจข้อความภาษาอังกฤษยาวๆ ที่มี Parameter เปลี่ยนไปเรื่อยๆ (เช่น IP, Block ID, ตัวเลข bytes) เราจึงต้องทำ **Log Parsing** เพื่อสกัดเอาเฉพาะ "รูปแบบของเหตุการณ์" (Event Template)

### 2.2 Function / Class สำคัญที่ใช้และเหตุผล

| Function / Class | Library | หน้าที่การทำงาน | ทำไมถึงใช้สิ่งนี้? |
|---|---|---|---|
| `MaskingInstruction` | `drain3.masking` | กำหนด Regex เพื่อแทนที่ตัวแปรผันแปร เช่น `<IP>`, `<BLK>`, `<NUM>` ก่อนเข้า Parser | ช่วยป้องกันไม่ให้ Drain3 สับสนคิดว่า IP คนละเบอร์หรือตัวเลขคนละค่าคือคนละ Template ทำให้จำนวน Event ไม่ระเบิด (Template explosion) |
| `TemplateMiner` | `drain3` | จัดกลุ่ม Log เข้า Parse Tree แบบ Prefix Tree ลึกคงที่ แล้วคืนค่า Event ID (เช่น E1, E2, ...) | เป็น State-of-the-Art Log Parser ทำงานเร็วระดับ O(1) ต่อบรรทัด และสกัดได้แม่นยำ 45 Templates ตรงกับฐานข้อมูลมาตรฐานของ Loghub 100% |
| `FilePersistence` | `drain3.file_persistence` | เซฟ State ของ Parser เก็บไว้ในไฟล์ `.bin` | ไม่ต้องเทรนสร้าง Template ใหม่ทุกครั้ง สามารถโหลดมาใช้งานต่อในระดับ Production หรือ Inference แบบ Real-time ได้ทันที |
| `train_test_split(..., stratify=y)` | `sklearn.model_selection` | แบ่งข้อมูลเป็น Train (70%), Validation (15%), Test (15%) | ใส่พารามิเตอร์ `stratify=y` เพื่อบังคับให้อัตราส่วน Anomaly 2.9% กระจายตัวเท่ากันทุกชุด ป้องกันการเกิด Data Leakage และ Bias |

> 🗣️ **บทพูดผู้บรรยาย (Phase 2):**
> *"เมื่อเรารู้จัก Log แล้ว ขั้นถัดไปคือการแปลงข้อความดิบให้เป็นโครงสร้าง (Log Parsing) ครับ*
>
> *เปรียบเทียบง่ายๆ เหมือนการตรวจคนเข้าเมือง ข้อความ Log มักจะมีชื่อคน วันที่ และเบอร์ IP ต่างกันไป แต่ใจความสำคัญของการกระทำคือ 'มีการดาวน์โหลดไฟล์' หรือ 'มีการเชื่อมต่อหลุด' สิ่งที่เราสนใจคือการกระทำนั้น*
>
> *เราเลือกใช้ **Drain3** ซึ่งเป็น Parser เชิงโครงสร้างต้นไม้ลึกคงที่ ร่วมกับ **Masking Instruction** เพื่อลบค่าตัวเลข IP และ Block ID ออก ผลลัพธ์คือเราสามารถยุบ Log 11.17 ล้านบรรทัด เหลือเพียง **45 Event Templates** ที่ชัดเจน (เช่น E5, E22)*
>
> *จากนั้นเราจัด Session ให้อยู่ในรูปของ Sequence (เช่น `E5 E22 E11 E5`) และแบ่งชุดข้อมูล Train/Val/Test แบบ **Stratified Split** เพื่อรักษาอัตราส่วนภัยคุกคาม 2.9% ไว้อย่างยุติธรรมครับ"*

## Phase 3: Baseline Models (Notebook 03)

### 3.1 ขั้นตอนนี้ทำทำไม? (Why do this?)
ก่อนที่จะกระโดดไปทำ Deep Learning ที่ซับซ้อน เราต้องมี "เส้นมาตรฐาน" (Baseline) มาเปรียบเทียบก่อนเสมอว่า ปัญหานี้สามารถแก้ได้ด้วยวิธีดั้งเดิมที่เบากว่าและเร็วกว่าหรือไม่

### 3.2 Function / Class สำคัญที่ใช้และเหตุผล

| Function / Class | Library | หน้าที่การทำงาน | ทำไมถึงใช้สิ่งนี้? |
|---|---|---|---|
| `CountVectorizer(token_pattern=r'\b\w+\b')` | `sklearn.feature_extraction.text` | แปลง Sequence ของ Event ID ให้กลายเป็นเวกเตอร์นับความถี่ (Event Count Vector) ขนาด 45 มิติ | วิธีดั้งเดิมที่ง่ายที่สุดในการป้อนข้อมูลเข้าโมเดลสถิติ โดยนับว่าใน 1 Session เกิด Event แต่ละแบบกี่ครั้ง (Bag of Events) |
| `LogisticRegression(class_weight='balanced')` | `sklearn.linear_model` | โมเดลจำแนกประเภทเชิงเส้น (Supervised Baseline) | เป็นสมการเชิงเส้นที่ตีความง่าย รวดเร็ว และใส่ `class_weight='balanced'` เพื่อชดเชยการที่ข้อมูลผิดปกติมีน้อย |
| `IsolationForest(contamination=0.03)` | `sklearn.ensemble` | โมเดลตรวจจับจุดผิดปกติแบบ Unsupervised โดยการสุ่มตัดแบ่งกิ่งไม้ (Isolation Tree) | จุดผิดปกติจะถูกตัดแบ่งให้โดดเดี่ยว (Isolate) ได้ง่ายและเร็วกว่าจุดปกติ ใช้ทดสอบกรณีที่ระบบไม่มี Label |
| `f1_score()` / `confusion_matrix()` | `sklearn.metrics` | คำนวณค่าเฉลี่ยฮาร์โมนิกระหว่าง Precision และ Recall | ดูแลทั้งสองด้าน: Precision (แจ้งเตือนแล้วไม่หน้าแตก) และ Recall (ไม่ปล่อยให้ผู้บุกรุกหลุดรอด) |

### 3.3 ผลลัพธ์และข้อจำกัดของ Baseline (จุดเปลี่ยนสำคัญ)
- **Logistic Regression:** ได้ F1-Score สูงถึง **98.02%**
- **Isolation Forest:** ได้ F1-Score **63.69%**

> 🗣️ **บทพูดผู้บรรยาย (Phase 3 & The ATM Analogy):**
> *"ในระยะที่ 3 เราสร้างโมเดลมาตรฐานเพื่อเป็นเกณฑ์วัด โดยใช้วิธีนับความถี่ของเหตุการณ์ (Event Count Vector)*
>
> *ผลลัพธ์คือ Logistic Regression ทำคะแนนได้สูงถึง 98.02% ฟังดูเหมือนปัญหาถูกแก้แล้วใช่ไหมครับ? แต่ในความเป็นจริง วิธีการนี้มี **'จุดบอดร้ายแรง'** ในเชิง Security ครับ!*
>
> *ขอเปรียบเทียบด้วย **Analogy ตู้ ATM**:*
> - *พฤติกรรมปกติ: `สอดบัตร -> กดรหัสผ่าน -> ถอนเงิน -> รับเงิน`*
> - *พฤติกรรมถูกแฮก: `สอดบัตร -> ถอนเงิน -> กดรหัสผ่าน -> รับเงิน`*
>
> *ถ้าเราใช้วิธีนับความถี่ (Count Vector) ทั้งสองกรณีเกิด Event เท่ากันเป๊ะ! โมเดล Baseline จะมองว่า 'ปกติ' ทันที เพราะมัน **ตาบอดต่อลำดับเวลาก่อนหลัง (Order-agnostic)** นี่คือเหตุผลว่าทำไมเราจึงจำเป็นต้องก้าวไปสู่ **Deep Learning ที่เข้าใจลำดับเวลา (Sequence Models)** ครับ"*

## Phase 4A: Supervised Session LSTM (Notebook 04)

### 4.1 ขั้นตอนนี้ทำทำไม? (Why do this?)
เพื่อแก้จุดบอดเรื่องลำดับเวลา เราสร้างโมเดล **Recurrent Neural Network (LSTM)** ที่สามารถจดจำประวัติของ Event ก่อนหน้า และตัดสินทั้ง Session ว่าเป็น Anomaly หรือไม่

### 4.2 Function / Class สำคัญที่ใช้และเหตุผล

| Function / Class | Library | หน้าที่การทำงาน | ทำไมถึงใช้สิ่งนี้? |
|---|---|---|---|
| `SessionDataset(Dataset)` | `torch.utils.data` | คลาสแปลง List ของ Token IDs และ Label ให้เป็น PyTorch Tensor | จัดการข้อมูลแบบ Custom รองรับลำดับความยาวที่ไม่เท่ากันในแต่ละ Session |
| `collate_sessions()` | Custom (in DataLoader) | ฟังก์ชันจับกลุ่ม Batch พร้อมทำ Zero-padding ให้ความยาวเท่ากัน | ใน Log จริง แต่ละ Session มีความยาวไม่เท่ากัน จึงต้องใช้ Collator เติม `<PAD>` ให้เป็น Tensor รูปสี่เหลี่ยมก่อนเข้า GPU |
| `nn.Embedding(vocab, dim, padding_idx=0)` | `torch.nn` | แปลง Event ID ตัวเลขเดี่ยวๆ ให้กลายเป็นเวกเตอร์ความหมายหนาแน่น (Dense Vector) | เรียนรู้ความสัมพันธ์เชิงความหมายระหว่าง Event ดีกว่าการทำ One-hot encoding ขนาดใหญ่ |
| `nn.LSTM(dim, hidden, batch_first=True)` | `torch.nn` | เลเยอร์ประมวลผลลำดับเวลา มี Forget Gate, Input Gate, Output Gate | ป้องกันปัญหา Vanishing Gradient ในการอ่าน Log ยาวๆ และจดจำลำดับก่อน-หลังของเหตุการณ์ได้สมบูรณ์ |
| `nn.BCEWithLogitsLoss(pos_weight=...)` | `torch.nn` | Loss Function ผสมระหว่าง Sigmoid และ Binary Cross Entropy พร้อมถ่วงน้ำหนักคลาส | ใช้คำนวณ Error โดยให้ความสำคัญกับคลาสผิดปกติ (ที่มีน้อย 2.9%) มากเป็นพิเศษผ่านค่า `pos_weight` |
| `tune_threshold()` | Custom (Evaluation) | ค้นหาค่าตัดเกณฑ์ (Threshold) ที่ให้ F1-Score สูงที่สุดบน Validation Set | ค่า Default 0.5 ไม่เหมาะกับข้อมูล Imbalance การจูน Threshold ช่วยดันให้ Recall พุ่งสูงถึง 99.80% |

> 🗣️ **บทพูดผู้บรรยาย (Phase 4A):**
> *"ในระยะ 4A เราพัฒนา **Supervised Session LSTM** ขึ้นมาครับ โมเดลนี้ประกอบด้วย:*
>
> *1. **Embedding Layer:** แปลง Event แต่ละตัวเป็นเวกเตอร์ต่อเนื่อง*
> *2. **LSTM Cells:** ทำหน้าที่ส่งต่อ Hidden State ไปตามลำดับ Event ทำให้โมเดล 'จำ' ได้ว่า Event ก่อนหน้าเกิดอะไรขึ้น*
> *3. **Class-Weighted Loss:** เราใช้ `pos_weight` ใน Loss Function เพื่อลงโทษโมเดลอย่างหนักหากปล่อยให้ Anomaly หลุดรอด*
>
> *และที่สำคัญคือเราใช้ฟังก์ชัน **Tune Threshold** บน Validation Set ทำให้เราได้คะแนน **F1-Score 98.71%** และทำ **Recall ได้สูงถึง 99.80%** หมายความว่าในการทดสอบจริง มี Session ผิดปกติหลุดรอดสายตาไปเพียง 0.2% เท่านั้นครับ!"*

## Phase 4B: DeepLog Next-Event Prediction (Notebook 04b)

### 4.1 ขั้นตอนนี้ทำทำไม? (Why do this?)
ในโลกความเป็นจริงของระบบ SOC การมี Label ระบุว่า "Log นี้คือการโจมตี" เป็นเรื่องที่ยากมาก เพราะภัยคุกคามแบบ **Zero-Day** จะไม่มี Label มาก่อน
เราจึงนำสถาปัตยกรรม **DeepLog ของจริง (Du et al., ACM CCS 2017)** มาสร้างระบบตรวจจับแบบ **Semi-supervised** ที่เรียนรู้จากเฉพาะ "ข้อมูลปกติ (Normal Only)"

### 4.2 Function / Class สำคัญที่ใช้และเหตุผล

| Function / Class | Library | หน้าที่การทำงาน | ทำไมถึงใช้สิ่งนี้? |
|---|---|---|---|
| `extract_sliding_windows(h=10)` | Custom | เลื่อนหน้าต่างขนาด $h$ ไปบน Sequence เพื่อสร้างคู่ `(ประวัติ 10 เหตุการณ์, เหตุการณ์ถัดไป)` | เลียนแบบพฤติกรรม Language Modeling คล้ายกับคีย์บอร์ดมือถือเดาคำถัดไปจากคำก่อนหน้า |
| `train_loader` (Normal Only) | `DataLoader` | ฟีดเฉพาะหน้าต่างของ Session ปกติเข้าสู่โมเดล | สอนให้โมเดลจำเฉพาะ **"ทางเดินที่ถูกต้องของระบบ"** เมื่อระบบทำงานปกติ |
| `detect_session_anomalies(top-k)` | Custom (Inference) | สำหรับแต่ละก้าวใน Session โมเดลจะทาย Event ถัดไปที่มีโอกาสสูงสุด $k$ อันดับแรก หาก Event จริงไม่อยู่ใน Top-$k$ จะถือว่าเป็นความผิดปกติทันที | หากระบบเกิด Event นอกเหนือจากที่โมเดลเคยคาดไว้แม้แต่ก้าวเดียว ก็สามารถส่ง Alert ให้ทีม SOC ตรวจสอบได้ทันที |

> 🗣️ **บทพูดผู้บรรยาย (Phase 4B):**
> *"อีกก้าวสำคัญที่พวกเราพัฒนาเพิ่มคือ **DeepLog Next-Event Prediction** ครับ*
>
> *แนวคิดนี้ฉลาดมาก เปรียบเหมือน **'ระบบเดาคำศัพท์บนมือถือ'** ถ้าเราพิมพ์คำว่า 'สวัสดี' มือถือจะเดาคำถัดไปเช่น 'ครับ', 'ค่ะ', 'ตอนเช้า'*
>
> *DeepLog ทำแบบเดียวกันกับ Log ระบบ: ถ้าเกิดเหตุการณ์ `E5 -> E22 -> E11` โมเดลจะทำนาย Top-$k$ ว่าเหตุการณ์ถัดไปควรเป็นอะไร โดยเราสอนโมเดลด้วยเฉพาะ Log ปกติเท่านั้น*
>
> *เมื่อนำไปตรวจจับ หากในระบบมีเหตุการณ์ที่ **'ไม่อยู่ใน Top-k ที่โมเดลคาดการณ์ไว้'** ระบบจะตัดสินทันทีว่าผิดปกติ! ข้อดีมหาศาลคือ **ไม่ต้องพึ่งพา Label การโจมตีเลย** และสามารถจับการโจมตีรูปแบบใหม่ๆ หรือ Zero-Day ได้อย่างทรงพลังครับ"*

## แผนการดำเนินงานระยะต่อไป (Slide 14)
1. **Transformer Encoder:** พัฒนาโมเดล Self-Attention เพื่อความสามารถในการตีความผล (Attention Weights Explainability) ชี้ชัดว่า Event ไหนทำให้เกิดการ Alert

## 💡 Q&A Cheat Sheet: คำถามที่อาจารย์มักจะถาม และแนวทางการตอบ

### Q1: ทำไมถึงเลือกใช้ Drain3 แทนที่จะตัดคำด้วย Regex ธรรมดา?
> **แนวคำตอบ:** *"Regex ธรรมดาต้องเขียนเงื่อนไขครอบคลุมเองทั้งหมด ซึ่งระบบ Log ขนาดใหญ่อาจมีรูปแบบเปลี่ยนแปลงตลอดเวลา แต่ Drain3 ใช้ขั้นตอนวิธี Parse Tree ลึกคงที่แบบอัตโนมัติ (Automated Tree-based Parsing) ทำงานได้รวดเร็วระดับ O(1) และไม่เกิดปัญหา Template ระเบิดจากตัวแปรครับ"*

### Q2: ทำไม F1-Score ถึงสำคัญกว่า Accuracy ในงานนี้?
> **แนวคำตอบ:** *"เพราะปัญหาเรื่อง Class Imbalance ครับ ข้อมูลเรามี Anomaly แค่ 2.9% หากโมเดลทาย 'ปกติ' ตลอดเวลา จะได้ Accuracy สูงถึง 97.1% แต่ตรวจไม่พบ Anomaly เลย (Recall = 0%) ดังนั้น F1-Score ซึ่งรวมทั้ง Precision และ Recall จึงเป็นตัวชี้วัดจริงที่บอกว่าโมเดลจับผู้บุกรุกได้จริงและไม่ส่งเสียงเตือนมั่วครับ"*

### Q3: ค่า Threshold ใน LSTM ที่บอกว่า 0.5 ไม่ดี ได้มาอย่างไร?
> **แนวคำตอบ:** *"เราใช้ฟังก์ชัน `tune_threshold()` โดยนำความน่าจะเป็นที่โมเดลส่งออกมาบน Validation Set มาทดสอบตัดเกณฑ์ตั้งแต่ 0.05 ถึง 0.95 แล้วคำนวณ F1-Score ทุกค่า ค่า Threshold ที่ให้คะแนน F1-Score สูงที่สุดคือค่าที่เราเลือกนำไปใช้จริงกับ Test Set ครับ"*

### Q4: DeepLog แบบ Next-Event กับ Supervised LSTM ต่างกันตรงไหน ทำไมต้องมีทั้งสองแบบ?
> **แนวคำตอบ:** *"Supervised LSTM ต้องใช้ข้อมูลทั้งปกติและผิดปกติในการเทรน เหมาะสำหรับระบบที่มีประวัติการโจมตีชัดเจน แต่ DeepLog Next-Event ถูกออกแบบมาสำหรับ Zero-Day Attack โดยเรียนรู้เฉพาะพฤติกรรมปกติ เมื่อใดก็ตามที่ระบบเดินผิดไปจากทางเดินปกติแม้แต่ก้าวเดียว มันจะแจ้งเตือนทันทีโดยไม่จำเป็นต้องเคยเห็นการโจมตีนั้นมาก่อนครับ"*
